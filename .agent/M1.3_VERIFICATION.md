## Status

**FAIL** (against M1 exit criteria "user can create and manage a complete trip
reliably") — but consistent with the M1.1/M1.2 pattern: a **documented gap**, not a
defect to patch now.

A created trip is a **group**. The group view (`#groupView`) exposes only
**"Bagikan grup" (invite)** and **"Keluar" (leave)**. There is **no delete and no
archive control** for a group trip. The personal `deleteTrip` ("Hapus trip ini")
button lives in `plannerView` and targets `state.trips` (empty for groups), so it is
never active for a group trip. "Leave" only removes the caller's own member row — it
does **not** delete or archive the group; the group and its data persist for other
members (and anyone holding the link).

---

## Flow tested

1. **Delete/archive entry point (group)** — `#groupView .planner-actions` = only
   `inviteGroupBtn` + `leaveGroupBtn`. No delete/archive button.
2. **Personal delete** — `deleteTrip` handler filters `state.trips` (personal only);
   never reaches a group trip.
3. **Leave behavior** — `leaveGroup()` deletes the caller's `group_members` row,
   clears local channel/poll, sets `colState.group=null`, returns home. It does **not**
   touch the `groups` row or other members' data.
4. **Archive capability** — none anywhere in the app (`hasArchive:false`).
5. **Persistence after leave** — group + data remain for remaining/other members.
6. **Validation / success / failure / refresh** — n/a (no delete/archive UI exists
   for groups).
