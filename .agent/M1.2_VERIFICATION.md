## Status

**FAIL** (against M1 exit criteria "user can manage a complete trip reliably").

The "Edit trip" capability is **not reachable for the produced artifact type**.
Because a created trip is a collaboration group, and the group view (`#groupView`)
has **no edit control**, a user cannot edit the trip's name / destination / dates
through the UI after creation. The personal-trip `editTrip()` handler resolves
`state.trips`, which is empty for a group trip, so it silently no-ops.

Important: the underlying **data layer supports editing** — a member `groups.update`
succeeds under RLS and propagates to other members (verified). So this is a
**missing UI/write-path gap**, not a backend impossibility.

---

## Flow tested

1. **Edit-trip entry point** — `#editTripBtn` (`editTrip()`) is bound only in
   `plannerView` (personal trips). `groupView` planner-actions expose only
   `inviteGroupBtn` (Bagikan grup) and `leaveGroupBtn` (Keluar) — **no edit button**.
2. **`editTrip()` resolution** — `getTrip()` = `state.trips.find(activeTripId)`.
   For a group trip, `activeTripId` is `null` and `state.trips` is empty →
   `editTrip()` returns early (`if(!trip||state.readOnlyTrip)return`).
3. **Data-layer edit capability** — `groups.update({name})` by a member succeeds
   under RLS; other members see the change (realtime + polling).
4. **Validation** — n/a at UI level (no edit form exists for groups). The create
   form's date/`required` validation is inherited (see M1.1).
5. **Success / failure / persistence** — n/a via UI. Via direct DB update: success
   + cross-member propagation confirmed.
